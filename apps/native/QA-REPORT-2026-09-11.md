## P0 — Blocking

### P0-1: Email OTP sign-in is completely broken on production
**Repro:** Fresh install → language → onboarding → Sign in → enter a real email → "Send me a code".
**Observed:** Red banner "Error sending magic link email" (`qa/2026-09-11/10-otp-sent.png`). No email ever arrives (verified by checking the mailbox for the address used). The raw Supabase error string is exactly `friendlyError()`'s fallback — it doesn't match any of the app's known-error regexes (expired / invalid+otp / rate-limit), so this isn't a case the client already understands.
**Expected:** A 6-digit code is emailed and sign-in proceeds.
**Impact:** Email is the primary, no-password sign-in path advertised on the screen itself ("No password — we'll email you a 6-digit code"). It is dead. Any user without a Google account, or who simply doesn't want to use Google Sign-In, cannot get into the app at all.
**Where to look:** `src/contexts/auth-context.tsx:203-212` (`sendCode` → `supabase.auth.signInWithOtp`). This is almost certainly a Supabase-side config issue, not a client bug — check the project's email-sending config/quota (free-tier Supabase auth email has a very low built-in rate limit and needs custom SMTP for production volume) and confirm the auth email template is actually set to send an OTP code, not a magic link (the UI promises "6-digit code" but the error text says "magic link email" — worth confirming the template matches the client's `verifyOtp` flow).
**Verified working around it:** Native Google Sign-In (`Continue with Google`) works correctly end-to-end — real account chooser, real session, lands in the app. This is the only usable sign-in path right now.

### P0-2: Chat composer cannot be used via direct tap — the flagship "Ask Sumaiya" feature is effectively broken
**Repro:** Home → Sumaiya tab → tap directly on the "Message Sumaiya…" text field.
**Observed:** Nothing happens. No keyboard, no cursor. Confirmed with `dumpsys input_method`: `mInputShown=false`, `mServedView=null` after the tap — this is not a screenshot-timing illusion, the OS itself never received a focus request. Reproduced 3 times independently, including from a clean re-entry into the chat tab.
**Workaround found:** Tapping one of the quick-action chips ("Just talk") does focus the field programmatically. Once focused this way, typing works fine and the message renders correctly in the composer.
**But then:** With a message typed and the send button showing its "active" (filled orange) state, tapping the send button (arrow icon, bottom-right) did **nothing** — no message sent, no bubble appended, and `adb logcat` shows zero `pro.sumaiya.app` activity in the seconds following the tap (confirmed by filtering out unrelated system/other-app noise). Pressing hardware Enter with the field un-focused instead moved D-pad-style focus to the screen's Back button, which is further evidence the TextInput isn't accepting real touch/focus input on this screen.
**Impact:** A first-time user's most natural action — tap the box, type, hit send — does not work. Users only escape this by noticing and tapping a quick-action chip first, and even then sending itself is unreliable. This is the assistant that the entire app onboarding sells ("Meet Sumaiya… I write your CV, target it, check it, prep you for the interview") — if the composer doesn't reliably accept input or send, that promise is broken from message one.
**Where to look:** `src/components/chat/chat-composer.tsx` (the `TextInput` and send `Pressable`, lines ~129-172) and `src/screens/sumaiya-chat-screen.tsx` (composer is inside a `KeyboardAvoidingView`, lines ~450-460). Ruled out during this audit: `AttachSheet` (`if (!visible) return null` — nothing left mounted) and `AttachmentPreviewSheet` (`if (!mounted) return null`, and it's a native `Modal` when shown, not an absolute-fill sibling) — neither should be able to leak a stray touch-blocking layer over the composer while closed, but something in this screen's touch/keyboard-avoidance handling is intercepting or misrouting taps in the composer's screen region. Worth checking `KeyboardAvoidingView`'s `behavior`/`keyboardVerticalOffset` on this specific device/Android version, and whether any `Animated.View` from the message list (`FadeIn`/`Layout` on message bubbles, `TypingDot`) extends a hit-testable area over the composer after layout settles.

### P1-2: "Your most recent job" wizard step accepts Continue with no real input
**Repro:** Sign-up wizard → "Your most recent job" step. Do nothing.
**Observed:** The field shows example text ("Storekeeper at Brookside, 2021–2024. Ran stock, GRNs and a team of 4.") that looks like normal input but is inert placeholder — confirmed by tapping in and pressing backspace 80× with no change, and by the field's `Continue` button already being enabled with zero real user interaction.
**Impact:** Not a fabrication risk (the placeholder is visually distinct enough, and testing confirmed it never gets submitted as real text), but it means this step doesn't actually enforce the "tell me one real thing" moment the wizard is designed around — a user can blaze through without Sumaiya learning anything about their actual last job. Given the app's stated anti-fabrication / evidence-based design goals, this step should require real typed input before `Continue` activates, the same way the "What do you work in?" and skill-picker steps correctly disable `Continue` until a real selection is made.
**Where to look:** the first-run wizard step component for "most recent job" (`apps/native/src/screens/first-run-screen.tsx` per the existing wizard, or its step sub-component) — likely a `Continue` gating condition that isn't checking the field's actual (non-default) value.

## P2 — Real but minor issues

### P2-1: Keyboard fully covers the active control on at least one wizard step
On "Your most recent job", opening the keyboard hides the `Continue` button completely (`qa/2026-09-11/20-post-wizard.png` vs `21-job-field.png`), forcing an extra manual keyboard-dismiss before the user can proceed. This is the exact class of regression the prior QA report flagged generally ("keyboard never covers active field") — confirmed here concretely.

### P2-2: Onboarding pagination dots render an inconsistent state
On the 4th/last onboarding slide ("I prep you for the interview"), the dot indicator shows two dots in the "active" (elongated, orange) style simultaneously (dots 2 and 4) instead of just the current one (`qa/2026-09-11/06-onboard4.png`). Cosmetic, but visible on every fresh install / every user.

### P2-3: CV editor's floating Save/Export bar overlaps the last content section
In the CV editor, the sticky bottom `Save`/`Export PDF` bar visually overlaps the top of the "Education" section header when scrolled to the bottom of the visible list (`qa/2026-09-11/30-new-cv2.png`) — the scroll content doesn't get enough bottom padding to clear the floating footer.

## P3 — Polish

### P3-1: Large dead vertical space on language-select and onboarding-carousel screens
Both the initial language picker and all 4 onboarding slides put their content in the top half of the screen with roughly 1000px of empty space before the CTA at the very bottom (`qa/2026-09-11/01-cold-start.png` and others). Consistent across every screen in that flow, so likely a shared layout template — worth a deliberate look, since on a tall device like this Pixel 8 Pro it reads as unfinished rather than intentional.
