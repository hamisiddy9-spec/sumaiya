## 1. The photo field can break out of its attribute (PROVEN XSS)

`apps/native/src/lib/cv-html.ts`

- Line 145: `const PHOTO_SRC_RE = /^(data:image\/(png|jpe?g|webp);base64,[A-Za-z0-9+/=]+|https:\/\/\S+)$/`
- Line 148: ``return `<img class="${className}" src="${p.profilePhoto}" alt="" />`;`

The `\S+` branch matches quotes and angle brackets, and the value is interpolated into an
attribute unescaped. Proof already run in Node: the string
`https://x/a"onerror="alert(1)` passes the regex and emits
`<img src="https://x/a"onerror="alert(1)" alt="" />`.

The write path is open: `profile.ts:24` (`photo: z.string().max(MAX_PHOTO_CHARS).optional()`),
`apps/web/lib/api/routes/mobile.ts:553`, and the shared `cv-shape.ts` schema all accept it.

Fix BOTH halves:
1. Tighten the https branch so it cannot match a quote, angle bracket or whitespace:
   `https:\/\/[^"'\s<>]+`
2. Escape the value where it is emitted at line 148, the same way the other fields in this file
   are escaped (match the file's existing `esc(...)` convention — read it first, do not invent a
   second escaping style).

Then check for the duplicated regex and the same emission bug elsewhere:
`apps/native/src/lib/cv-engine/photo.ts:12` (the same regex appears there) and any other place
that interpolates `profilePhoto` into markup. Fix the duplicates the same way.

Test: `apps/native/src/lib/cv-html.test.ts:34` currently tests only a SPACED payload, which is why
this survived. Add cases that assert REJECTION for `https://x/a"onerror="alert(1)` and for
`https://x/a><script>` (the result must be the empty string / the no-photo path, not an `<img>`),
and one case asserting a legitimate `https://...` and one legitimate `data:image/jpeg;base64,...`
still render. Run the suite and quote the output.

## 2. The email-confirmation deep link validates by substring

`apps/native/src/contexts/auth-context.tsx:103`

```ts
if (!url || !url.includes("auth/confirm")) return;
```

That is the ONLY guard, and it is a substring test — any URL that merely contains `auth/confirm`
proceeds, and the handler then reads `access_token` / `refresh_token` out of the fragment and calls
`supabase.auth.setSession({...})`. Replace it with an exact match of scheme + host + path for the
real link (`sumaiya://auth/confirm`), and return early for anything else. Keep the genuine flow
working: the real confirmation link and the `token_hash` / `error_description` branches must still
work. Add a test that a decoy URL containing the substring but not the exact link is ignored.

## 3. The session leaves the device in the cloud backup (found on the shipping APK)

The release APK manifest has `android:allowBackup="true"` with ZERO exclusion rules, and
`apps/native/src/lib/supabase.ts:42` stores the Supabase session in plain `AsyncStorage`. Verified
on a Pixel 8 Pro: `bmgr backupnow pro.sumaiya.app` succeeds and uploads ~85KB of app data to the
Google Drive transport. Consequence: after a reinstall or a phone migration, Android can restore
that blob — including a live `access_token`/`refresh_token` — and the app comes back signed in, on
a possibly different device or account.

Fix: make the auth data non-restorable.

- Preferred if you can do it cleanly: exclude the auth store from backup via
  `dataExtractionRules` (Android 12+) and `fullBackupContent` (older) XML in the checked-in
  `apps/native/android/` project, referenced from its `AndroidManifest.xml` — keeping backup for
  the user's documents.
- Otherwise: set `android.allowBackup` to `false` in `apps/native/app.json`.

State plainly in your report which one you did and why. Do NOT put the session value directly into
`expo-secure-store` — it caps values at 2048 bytes on Android and a Supabase session with its JWT
exceeds that. If you attempt an encrypted-at-rest store, use a key held in SecureStore with the
ciphertext in AsyncStorage, and say so.

## 4. A signed-out user has no way back into their account (reproduced on the Pixel)

deliberate (`apps/native/src/navigation/root-navigator.tsx:19` — GUEST MODE replaced
`!user ? AuthStack : App`) and the guest-first intent must SURVIVE: a first-time user must still be
able to build and download a CV without an account.

The defect is the consequence:

  the sublabel `Your CVs are saved on this phone. A free account keeps them for you.` /
  `CV zako zimehifadhiwa kwenye simu hii...`
- A returning user is therefore told they have NO ACCOUNT, on a screen reading `No CVs yet`, with
  their real CVs on the server and no route to them. After a data clear the device-CVs line is also

- A grep for a sign-in affordance across the signed-out UI finds nothing: the only `Sign in` /
  `Ingia` lives inside `screens/auth/sign-in-screen.tsx`, which the guest UI cannot reach.

Do this:
1. Give a signed-out user a visible, obvious way to sign in (`Ingia` / `Sign in`) — on the home

2. Correct the copy so it (a) never asserts that a signed-out user has no account, and (b) never
