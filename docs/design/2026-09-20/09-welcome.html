DThe shared language that binds the sequence

D1 · ONE entry idiom

the idiomrise
distance12px (the standard’s rise)
enteringdur.slow 300ms · ease.out
leavingdur.fast 140ms · ease.in

If something rises, everything rises. Horizontal motion is reserved for push/pop between screens, and the splash’s overshoot stays the standard’s one sanctioned exception — it is the only element allowed to be different, and that is what makes it feel like a signature rather than a mistake.

D2 · ONE duration family

entering300 (dur.slow)
in place220 (dur.base)
leaving140 (dur.fast)
a screen push260 (dur.screen)
the root mode switch340 (dur.field)

Five tokens replace thirteen ad-hoc numbers. Nothing in the welcoming path needs a duration that is not already defined.

D3 · ONE progress treatment

forma bar that persists across steps
slidesthe same bar, same height, same colour
nevera per-screen counter that resets

Today the slides use three dots, first-run uses a “Hatua 3 kati ya 8” line, and neither survives its screen. One bar, one geometry, carried across every step — it is the cheapest possible continuity signal and the one the user reads as “I am X% of the way in”.

D4 · ONE type and spacing rhythm

screen headingDisplay 30/36/800/-0.5
bodyBody 14.5 or BodySmall 13.5
padding20 screen · 16 card
gaps4 · 8 · 12 · 16 · 20 · 24 · 32

The welcoming path currently rolls its own sizes per screen. Under the design system it is the same nine roles as everywhere else, which is what makes six screens look like one product.

D5 · THE HAND-OFF — what makes it continuous

This is the rule that actually fixes his complaint. One object travels. At every boundary something from the outgoing screen is still present in the incoming frame:

launch → languagethe mark shrinks to the header and stays
language → slidesthe chosen language’s code persists as a chip
slides → first runthe progress bar is the same object
step → stepthe entered value persists where it was typed
first run → sign-inthe name/email already typed is shown, not asked again
sign-in → homethe root fade arrives over an already-painted home

No new animation is required for any of these. Each is a layout decision: keep one element mounted across the boundary and the sequence stops being a queue of screens. The outgoing content leaves at dur.fast while the incoming arrives at dur.slow — never one after the other, which is what produces the blank beat the user reads as a new app starting.

D6 · One theme across the whole path

The pre-auth path is legitimately a light brand runway (root-navigator.tsx pins ThemeScope mode="light" and that is a good decision). The defect is that the container does not share it: rootScreenOptions(c) paints c.bg from the unpinned theme, so on a dark-mode phone the gaps between the light screens are dark. One fix: the root container’s contentStyle.backgroundColor must be the same cream the pinned screens use. Nothing else changes, and the flash disappears.

FWhat the device showed, and what it disagreed with

A 6.3 MB screenrecord of a real cold start on the owner’s phone (1344×2992, density 408), 12 frames extracted at 0.5s spacing, judged by a free vision model. The frames are in _device/welcome-contact-sheet.png.

What the frames show (measured, not inferred)

frame 1cream background, mark in a CIRCLE
frames 2-3dark background, COMPLETELY BLANK (~1s)
frame 4cream background, mark in a ROUNDED SQUARE
frames 5-12dark home with content
background ordercream → dark → dark → cream → dark

The model read the background order as “white → black → black → white → black” and said “the white-to-black switch would be perceived as a flash”, and that the logo “appears twice … the symbol is identical, but the container differs (circle vs. square), so it is not identical”. Both are its readings of real pixels and both corroborate the owner.

Where the model disagreed with the owner

Asked whether the sequence reads as one arrival or as unrelated screens, it answered: “It reads as ONE continuous cold-start arrival. The only possible break is frames 2-3 (blank black), but they are part of the loading sequence, not unrelated screens” and “This is a designed welcome sequence, not a disjointed stack of separate pieces.”

I am reporting the owner’s read over the model’s. Two reasons, stated so he can judge: the model was shown the cold start only — the part of the path he is most likely to be describing is the slides and first-run steps, which I could not re-trigger without clearing his app data (forbidden). And its factual readings (the flash, the two containers, the blank second) support the complaint even where its verdict did not. A judgement of “does this feel like one arrival” is also precisely the kind of impression a vision transcript is weakest at.
